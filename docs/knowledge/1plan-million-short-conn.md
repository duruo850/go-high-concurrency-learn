# 百万短连接瞬间高并发接入方案（Go）

> **核心判断：** 矛盾不是「同时维持几百万连接」的内存，而是 **几百万次建连/断连在极短窗口叠加**，从内核协议栈打到 Go runtime 的级联链。  
> **设计目标：** 不是扛住几百万连接同时存在，而是让建连/断连 **不在同一瞬间压垮同一个队列**。  
> 场景：短连接（建连 → 少量请求 → 断开）；活动开闸、故障恢复、集中重连等。  
> 读法：先读 **§0 概要** → **§A/§B** → 后文分层方案（每项：干什么 / 谁做 / 不是什么）。

---

## 0. 概要：是什么 → 为什么 → 怎样做 → 怎么验证

### 0.1 是什么（定性）

- 这是 **建连风暴（CPS 洪峰）**，不是「百万长连接挂机」模型。  
- 短连接 goroutine 生命周期短，但 **建连频率极高**；先爆的往往是 accept 队列、TIME_WAIT、端口池、netpoller 高频唤醒带来的调度抖动。  
- 腾讯会议类产品：媒体是长连接；**信令/入会控制面** 仍可能大量短连接——本文焦点在后者。

### 0.2 为什么：一条级联链 + 四环

```text
短连接洪峰 → accept 队列满 → 客户端超时重试放大 CPS
         → 主动关闭方 TIME_WAIT 占资源（端口或 FD/内存）
         → 处理变慢、队列更排空 → epoll 高频就绪 → GMP 调度抖动
```

| 环 | 一句话 |
|----|--------|
| **① accept 队列** | 全连接队列上限约 `min(backlog, somaxconn)`；满后丢第三次握手 ACK，客户端以为连上了却超时；`listen overflow` 会涨。调大 somaxconn 只推迟填满。 |
| **② TIME_WAIT** | 主动关闭方在约 2MSL（~60s）占住四元组。短连接下占用 ≈ `每秒主动关闭数 × 60`。 |
| **③ 端口耗尽** | **主动外连** 侧：临时源端口不够 → `Cannot assign requested address`；重启进程清不掉内核 TIME_WAIT。要分清本机是「被连」还是「主动连别人」。 |
| **④ epoll / GMP 抖动** | fd 高频注册/注销，`epoll_wait` 频繁返回；M/P 解绑重绑，非自愿上下文切换升高。往往 **P99/重试先坏，不是 QPS 先掉**。 |

**TIME_WAIT 卡住什么（两侧不同）：**

| 侧 | 卡住的资源 | 典型后果 |
|----|------------|----------|
| **客户端 / 主动外连** | 临时 **源端口** | 无法再建到同一目标 |
| **服务端主动踢连接** | **FD + 内核内存**（监听端口本身不耗尽） | `Too many open files`，`accept` 失败 |

供需一句：**新建消耗速率 > TIME_WAIT 回收速率**。治本是 Keep-Alive/连接池少产生 TW；`tcp_tw_reuse` 等只辅助，且主要利好出站侧。

**系统级瓶颈三层（FD → 内存 → 内核栈）：**

1. **FD**：最常见第一道墙（默认常 1024）；调 `ulimit`/`file-max` 后瓶颈后移。  
2. **内存**：空闲连接约数 KB 级内核态；活跃连接含 buffer 可到数十 KB+。FD 够但内存不够 → `ENOBUFS`/`ENOMEM`。  
3. **内核网络栈**：中断、拷贝、锁竞争；冲到 C10M 才常要 DPDK/io_uring 等旁路思路——本文百万短连洪峰优先把 ①②③④ 和接入收敛做好。

### 0.3 怎样做：五层收敛（对应后文）

| 层 | 做什么 | 详见 |
|----|--------|------|
| **① 入口收敛** | L4 接握手；L7 做 TLS/路由/鉴权/限流；多 AZ 就近；洪峰切成可控流量 | §2 |
| **② Go 进程** | Accept 不停；软丢载 + 硬 LimitListener；业务舱壁有界 | §4 |
| **③ 内核/runtime** | somaxconn；分清主动关闭方再谈 `tcp_tw_reuse`；必要扩端口范围；盯非自愿切换 | §5、§6 |
| **④ 短而不重** | `sync.Pool`、出站连接池；协议允许则 Keep-Alive/H2 少建 TCP | §1.4、§3、§4 |
| **⑤ 背压** | accept 前 LB/网关限流；进程内软限 Close / HTTP 503；识别重连风暴 | §1、§2.5、§4、§7 |

### 0.4 怎么验证（别只看 QPS）

| 类 | 看什么 |
|----|--------|
| accept | `listen overflow`、`ss -lnt` 的 Recv-Q/Send-Q |
| TW / 端口 | `ss -s`、临时端口占用、`Cannot assign requested address` |
| Go | `nonvoluntary_ctxt_switches`、goroutine 数、GC、netpoll 等待 |
| 业务 | P99、快速失败/503 比例、重试是否二次放大 |

短连接洪峰下常见：**延迟和重试先恶化，QPS 后掉**。

## A. 应该有的架构（先画清楚）

「几百万同时在线 / 同时连上」**正确架构一定是集群**，不是一个 Go 二进制。推荐分层如下：

**完整架构（推荐看这张）：** [../high-concurrency-full-arch.svg](../high-concurrency-full-arch.svg)  
展示层 → **接入层（DNS + L4/L7 + 网关能力合并）** → **业务层（微服务）** → **基础层**；右侧治理 / 运维。

**精简链路：** [../high-concurrency-arch.svg](../high-concurrency-arch.svg)

#### 接入网关 和 L4/L7 是否重复？

**会重复——如果两层都只做「把流量分到后面机器」。**

| 组件 | 真正该干的事 | 和另一层关系 |
|------|----------------|--------------|
| **L4/L7 负载均衡**（F5/SLB/云 NLB/ALB） | 四层/七层把连接打散；常做 **TLS 卸载** | 入口分流，必留 |
| **Nginx / API 网关** | **认证、鉴权、路由到微服务、限流、建连限流** | 能力可挂在 Nginx/网关产品上，与 LB **同属接入层** |

推荐画法（本图已改）：

```text
DNS / 就近 → L4/L7 负载均衡（打散 + TLS 卸载）→ Nginx/网关能力（鉴权·路由·限流）→ 微服务
```

**不要再单独叠一层「只做负载均衡的接入网关」**，那会和 L4/L7 语义重复。参考图里「接入级 F5/SLB + Nginx + 网关功能」应理解成 **同一接入层里的不同能力**，不是三次重复分流。

```text
                    ┌─ 客户端消峰（jitter / 退避 / 分批开闸）
                    │
用户/App ──HTTPS──►│
                    ▼
            ┌───────────────┐
            │ DNS / 就近接入 │  同地域多 AZ
            └───────┬───────┘
                    ▼
            ┌───────────────┐
            │ L4/L7 负载均衡 │  打散；TLS 卸载
            │ SLB / NLB 等   │
            └───────┬───────┘
                    ▼
            ┌───────────────┐
            │ 接入网关/边缘  │  建连限流、WAF、可选长连接网关
            │ Nginx/APISIX  │
            └───────┬───────┘
         ┌──────────┼──────────┐
         ▼          ▼          ▼
    ┌────────┐ ┌────────┐ ┌────────┐
    │ Go 业务 │ │ Go 业务 │ │ Go …  │   ← 每个进程只扛「分摊后的一份」
    │ 实例 1  │ │ 实例 2  │ │        │
    └────┬───┘ └────┬───┘ └────┬───┘
         └──────────┼──────────┘
                    ▼
            ┌───────────────┐
            │ Redis/MQ/DB   │  有界、可削峰；重活异步
            └───────────────┘
```

### A.1 三种「连接」别混在一张图里

| 类型 | 用户体感 | 服务端本质 | 架构要点 |
|------|----------|------------|----------|
| **短连接 API** | 打开活动页、点一次下单 | TCP 建了又拆，或短 Keep-Alive | **本文焦点**：消峰 + LB + 限流拒连 |
| **长连接在线** | IM/在线状态/信令一直挂着 | WebSocket 等挂很久，心跳轻 | 接入长连接集群；业务与连接可分离 |
| **音视频通话** | 能看能说 | 信令 + **媒体 SFU/MCU** | 信令可用 Go；**媒体单独集群** |

**几百万「人」：** 落在 **很多 Go 实例（+ 媒体节点）之和** 上。  
**一个 Go 进程：** 只是上图里的「实例 1/2/…」之一。

### A.2 设计原则（和架构绑定）

1. **别让几百万建连打到同一个队列/进程** → LB + 多实例 + 限流。  
2. **能少建连就少建连** → Keep-Alive / HTTP2 / 长连接 / 客户端错峰。  
3. **建连也可拒绝** → 网关限流 + 进程内软丢载/硬上限/HTTP 503，超额快速失败。  
4. **在线人数 ≠ 视频路数** → 信令在线与媒体路数差一个数量级以上。

## B. 一个 Go 进程支持多少「在线」？（先给数，再谈优化）

> 下列是 **数量级经验值**，用于定架构与机器规划；上线必须以 **同机型压测** 为准。  
> 「在线」必须先定义清楚：只挂连接？还是在跑业务？还是在跑视频？

### B.1 先定义你说的「在线」

| 你说的「在线」 | 实际负载 | 单进程主要卡在 |
|----------------|----------|----------------|
| **① 短连接瞬间涌入** | 同时 dial / TLS / accept | SYN 队列、fd、握手 CPU、goroutine 尖峰 |
| **② 长连接挂机在线** | WebSocket 已连上，心跳/轻信令 | fd、内存/连接、心跳扇出 |
| **③ 在线且高频 API** | 连接在 + 每秒很多业务请求 | 业务 CPU、下游 DB/Redis |
| **④ 视频能正常聊** | 信令在 + 音视频进出 | **带宽与媒体 CPU**（常不是这个 Go 业务进程） |

### B.2 单 Go 进程——建议按这个数量级做容量规划

假设常见云主机量级（约 4～8 核、8～16GB，Linux 调过 fd；**有 TLS 时更吃 CPU**）：

| 场景 | 单进程「舒适区」数量级 | 含义（说人话） | 再往上怎么做 |
|------|------------------------|----------------|--------------|
| **① 短连接并发（已 accept、短生命周期）** | **数千～1～2 万** 并发连接较常见讨论区；TLS+业务时更容易掉到 **数千** | 不是稳态「聊天在线」，是同时握在手里的 TCP | 多实例；拒超额；少建连 |
| **①′ 短连接新建速率 CPS** | 单机 **千～数千 conn/s** 就要认真看队列与 TLS | 「同时连上」往往先爆在 CPS，不是总人数 | 客户端错峰 + 网关限 CPS |
| **② 长连接纯在线（心跳轻、几乎无媒体）** | **1 万～5 万**/进程可作规划起点；优化好可达更高，**不保证 10 万+人人轻松** | 「挂着」便宜，「每个人狂发消息」不便宜 | 长连接集群水平扩 |
| **③ 长连接 + 明显业务 QPS** | 常被下游拖死，连接数目标要 **下调** | 瓶颈在 DB，不在「还能不能 accept」 | 缓存、异步、限流 |
| **④ 视频会议式「能沟通」** | **不要用业务 Go 的连接数当视频容量** | 媒体 SFU：一对一常按 **百～低千「端」/媒体节点**；多方会议室单机常按 **几十～一两百人级** 想 | 独立媒体集群；按房间调度 |

**直接回答「一个 Go 进程多少人在线」：**

- 若指 **② 长连接挂机在线（类 IM 在线、不是腾讯会议视频面）**：规划上先按 **约 1 万～5 万/进程**，压测后再定；几百万 = `进程数 × 单进程上限 × 冗余`。  
- 若指 **① 短连接活动开闸**：别谈「在线人数」，谈 **CPS + 并发连接上限**；单进程通常 **远小于** 长连接挂机数，靠集群 + 拒连。  
- 若指 **④ 腾讯会议那种能看能说**：一个业务 Go **不负责**这个数字；看 **媒体节点** 带宽/转发能力，业务 Go 只做信令时可仍按 ② 估「在房信令人数」。

### B.3 为什么不是「几百万/进程」

粗账（仅示意）：

```text
每条长连接粗算：1 个 fd + 至少 1 个 goroutine + 缓冲/状态（数 KB～数十 KB 量级，视实现）
100 万连接 → 仅内存就可能到数 GB～数十 GB，fd/调度也先爆
再加 TLS 握手风暴 → CPU 先死
```

所以：**几百万是集群目标；单进程目标是「可拒绝、可观测的上限」。**

### B.4 单进程怎么定自己的上限（落地）

```text
单进程上限 ≈ min(
  ulimit/fd 余量,
  内存 / 每连接实测开销,
  CPU 能撑的 CPS 与业务 QPS,
  下游（Redis/DB）能撑的 QPS
)
```

进程内用 **软丢载 + 硬 LimitListener**（§4）：到达上限 **立刻拒绝**，宁可 503，也不让进程 OOM/假死。  
集群容量：

```text
集群可服务在线 ≈ 单进程上限 × 实例数 × (0.5～0.7 冗余系数)
```

## C. 本文后半在解决什么问题

焦点是 **建连风暴（thundering herd）**，不是稳态 QPS。痛点与 §0.2「一链四环」一致：

| 维度 | 短连接风暴时真正疼的点 |
|------|------------------------|
| 内核 | SYN/`accept` 队列、TIME_WAIT、端口或 FD |
| 文件描述符 | 每连接至少 1 个 fd；服务端 TW 也会占 FD |
| Go runtime | 短生命周期 G 风暴、netpoll 高频唤醒、调度抖动 |
| TLS | 握手 CPU（应用层未卸载时） |
| 下游 | 鉴权、DB、Redis 被瞬时打穿 |

下面从客户端 → 接入 → 协议 → 单机 Go → 内核 → 下游展开（每项：干什么 / 不是什么）。

---

## 1. 客户端侧：消峰

短连接风暴很多是客户端「同一时刻一起连 / 失败后立刻重连」造成的。下面五项都发生在 **客户端或 SDK**，不是重启服务端。

### 1.1 重连抖动（jitter）

**干什么：** 要连（或失败后要重连）之前，先随机睡一小段时间，再 dial。  
**谁做：** App / 小程序 / 游戏客户端 / SDK。  
**不是什么：** 不是随机重启；不是服务端随机踢人。

```text
开闸或失败后：
  wait = random(0, T)   // 例如 T=10s，每人抽到 0～10 秒不等
  sleep(wait)
  dial()
```

**效果：** 若 100 万人本来在同一秒连，变成摊在 10 秒内陆续连，峰值 CPS 约降一个数量级。  
**常和退避一起用：** 先算退避基数，再乘/加减随机因子。

---

### 1.2 指数退避 + 上限

**干什么：** 连不上或请求失败后，**进程不退出**，只 `sleep`；等待时间 1s→2s→4s…，有封顶。  
**谁做：** 客户端。  
**不是什么：** **不是重启 Go 服务，不是重启 App**；只是「这次先别连，过会儿再试」。

触发（算一次失败）：

- TCP/TLS 建连失败、超时  
- HTTP 429 / 503 / 502  
- 业务返回「系统繁忙，请重试」

```text
第 1 次失败 → 等 1s  → 再 dial
第 2 次失败 → 等 2s  → 再试
第 3 次失败 → 等 4s  → 再试
… 直到 maxDelay（如 30s）封顶，之后每次都等 30s
成功一次 → delay 重置回 1s
```

```text
delay = 1s
maxDelay = 30s
loop:
  if DialAndRequest() 成功:
    delay = 1s
  else:
    sleep(delay)                    // 睡觉，不重启
    delay = min(delay*2, maxDelay)
```

| 误解 | 正解 |
|------|------|
| 1s→2s 是重启？ | 否，是 sleep |
| 「上限」是最多连几次？ | 通常指 **等待时长封顶**；也可另配「最多重试 N 次后弹窗放弃」 |

**为什么要：** 失败立刻重连会把刚缓过来的机器再次打挂；拉长间隔 = 主动让路。

---

### 1.3 分片开闸

**干什么：** 按用户/设备算一个「允许开始连接的时间偏移」，让百万人不要同一秒开闸。  
**谁做：** 客户端按规则算，或服务端下发「你的放行时间」。  
**不是什么：** 不是把用户永久踢掉；是 **错峰几秒到几十秒**。

```text
offset = hash(userId) % 60          // 0～59 秒
开闸时刻 T0 之后：
  if now < T0 + offset: 显示排队/倒计时
  else: 允许 dial
```

**效果：** 百万用户均匀摊在约 60 秒内接入。  
**和 jitter 区别：** 分片是「按身份固定错开」；jitter 是「再加随机」。可叠加。

---

### 1.4 本地连接池 / HTTP Keep-Alive

**干什么：** 同一台客户端到同一主机，**尽量复用已有 TCP**，不要每个 API 都新建一条连接。  
**谁做：** HTTP 客户端库（Go 的 `http.Transport`、OkHttp、浏览器等）。  
**不是什么：** 不是服务端连接池（那是 DB 连接池）；这里是 **客户端出站复用**。

```text
差：  请求1 dial→用完 close；请求2 再 dial→close   // 两次完整 TCP(+TLS)
好：  dial 一次 → 请求1 → 请求2 → … → 空闲一段时间再 close
```

Go 客户端侧常见：

- 复用同一个 `http.Client` / `Transport`（不要每次 `http.Get` 都新建 Client 且关 Keep-Alive）  
- `Transport.MaxIdleConns`、`IdleConnTimeout` 配好  

**效果：** 「短连接次数」下降；建连风暴压力直接变小。  
**注意：** 服务端也要允许 Keep-Alive（不要每个响应都 `Connection: close`）。

---

### 1.5 改成长连接或多路复用（客户端协议选择）

**干什么：** 少建 TCP，一条连接上跑很多次业务。  
**谁做：** 协议选型 + 客户端实现。  
**不是什么：** 不是「连接永远不断开就万事大吉」——长连接也要心跳、踢空闲、水平扩容。

| 形态 | 具体干什么 |
|------|------------|
| HTTP/2 | 一条 TCP 上多个 stream 并行请求 |
| gRPC | 默认 HTTP/2；可再上 stream |
| WebSocket / 自研长连接 | 先连上一直挂着，业务用消息帧，而不是每次业务新建 TCP |

**效果：** 「业务高峰」≠「建连高峰」。  
细节见 §3。

---

### 1.6 产品侧：分批进入 / 排队页 / 预约制

**干什么：** UI 层不让所有人点按钮就立刻打 API。  
**例子：** 进入活动页先拿排队号；轮询「是否轮到你」；轮到了才允许下单接口。  
**不是什么：** 不是技术偷懒，是把「同时」改成「可预期斜坡」——和工程方案同等重要。

---

## 2. 接入层：水平打散 + 准入

流量在进 Go 业务进程之前，先经过 LB / 网关。

### 2.1 多可用区 + 多实例负载均衡

**干什么：** 几百万连接 **分摊到 N 台机器**；每台只扛 `总量/N`。  
**谁做：** 云 SLB/NLB、Nginx、Envoy、K8s Service 等。  
**不是什么：** 不是一台机器垂直升配就能替代；几百万同时短连必须水平拆。

```text
客户端
  → DNS 解析到接入 VIP
  → L4/L7 LB 按策略分发
  → Go 实例1、实例2、… 实例N
```

**你要算的账：** 单机可接受上限（见 §6）× 实例数 ≥ 峰值目标（还要留冗余）。

---

### 2.2 就近接入（同地域多 AZ）

**干什么：** 用户、LB、源站放在同一地域（可多 AZ），降低 RTT；把全局瞬时洪峰切成区域分批流量。  
**为什么和「扛连接」有关：** RTT 越低，握手越快完成，半连接占用时间越短，同样 CPS 下队列更不容易堆死。  
**不是什么：** 不是跨大洲多活的全部方案；这里强调 **同地域降延迟 + 洪峰切分**。

---

### 2.3 TLS 卸载

**干什么：** 证书和 TLS 握手放在 SLB/Nginx/Envoy 上做完；后面到 Go 用内网明文 HTTP 或内网 mTLS。  
**谁做：** 接入层。  
**不是什么：** 不是取消加密（公网仍是 HTTPS）；是 **别让每台 Go 业务机都做百万次公钥运算**。

```text
客户端 --HTTPS--> LB（终结证书）--HTTP/内网--> Go
```

**效果：** 短连接场景下，CPU 往往从「被握手打满」变成「还能跑业务」。

---

### 2.4 SYN 代理 / 云防护

**干什么：** 在云网络边界限制异常 SYN 速率、挡 CC；合法握手再进你的 LB。  
**谁做：** 云 WAF/抗 D、高防、SYN Proxy 类产品。  
**不是什么：** 不能替代应用限流；它解决的是 **内核队列在到达 Go 前就被打爆 / 被攻击**。

---

### 2.5 接入网关「建连限流」与快速失败

**干什么：** 在 Nginx / APISIX / Envoy 限制 **同时连接数** 或 **新建连接速率**；超了直接拒绝，不把压力传给 Go。  
**不是什么：** 不是只限「每秒请求数 QPS」。短连接风暴首先是 **CPS（每秒新建连接）** 和 **并发连接数**。

| 手段 | 含义 |
|------|------|
| 限并发连接 | 例如每 IP / 全局最多 N 条 TCP |
| 限新建速率 | 例如每秒只放行 M 次新握手（常用漏桶 / 令牌桶实现） |
| 快速失败 | 超限返回 503 或直接断连；**比排队拖死后端更健康** |

客户端收到 503 后应走 §1.2 退避，而不是立刻重连。  
Go 进程内再做第二道：软丢载 + 硬 LimitListener + HTTP 503（§4）。

#### 2.5.1 漏桶限流（Leaky Bucket）

**干什么：** 请求先进「桶」里排队；桶底以 **固定速率** 往外漏（处理）；桶满了再来的直接拒绝或丢弃。  
**形象：** 水桶上面进水、下面匀速漏水——出口永远平稳，入口突发会被桶缓冲或溢出。

```text
请求 ──► [ 桶容量 = B ] ──固定速率 r/s──► 后端
              │
         桶满则拒绝（快速失败）
```

| 点 | 说明 |
|----|------|
| 平滑性 | **强**：对外输出速率被压成近似恒定，适合保护后端「只能匀速吃」的场景 |
| 突发 | 只能靠桶里已有空位吸收；桶小则几乎不允许突发 |
| 建连场景 | 例如：全局 accept/放行速率固定为 `r` CPS，多出来的握手直接断 |

伪代码直觉：

```text
bucket = queue(max=B)          // 最多积压 B 个待处理连接/请求
漏水协程：每 1/r 秒从 bucket 取 1 个交给后端

来新连接：
  if bucket 未满: 入队
  else: 立刻 Close / 503     // 快速失败
```

**不是什么：** 不是「平均速率 lim 一下、偶尔允许很大尖峰」——漏桶刻意把尖峰削平。  
**和令牌桶差别：** 漏桶限制的是 **流出速率**；令牌桶限制的是 **流入是否持有令牌**，可保留突发能力。

#### 2.5.2 令牌桶限流（Token Bucket）

**干什么：** 系统按速率往桶里放「令牌」；每个连接/请求要先拿到 1 个令牌才能过；没有令牌就拒绝。桶内令牌有上限，故允许短时突发。  
**形象：** 饭堂发餐券，每秒发 r 张，口袋最多攒 B 张——人多时先花攒下的券，花光了就得等或被拒。

```text
          每秒放入 r 个令牌（最多堆到 B）
                    │
                    ▼
请求 ──拿令牌──► [ 令牌桶容量 = B ] ──有令牌则通过──► 后端
                    │
               无令牌则拒绝
```

| 点 | 说明 |
|----|------|
| 平均速率 | 长期不超过 `r`（令牌发放速率） |
| 突发 | 桶满时一口气可过最多 `B` 个（短时尖峰），适合接口有自然毛刺的流量 |
| 建连场景 | 例如：`r=2000` CPS，`B=5000` → 平均每秒约 2000 新连接，瞬间最多积 5000 个令牌对应的突发 |

伪代码直觉：

```text
tokens = B                    // 初始满桶
每秒：tokens = min(B, tokens + r)

来新连接：
  if tokens >= 1:
    tokens -= 1
    放行
  else:
    立刻 Close / 503
```

**不是什么：** 不是无上限狂放；`B` 就是突发上限，要按单机/集群承受力设。  
**常见落地：** Nginx `limit_req`（漏桶思路）、APISIX/Envoy 的 rate-limit 插件、Go 侧 `golang.org/x/time/rate`（令牌桶）。

#### 2.5.3 两种机制怎么选（建连场景）

| | **漏桶** | **令牌桶** |
|--|----------|------------|
| 出口形态 | 更平滑、匀速 | 允许受控突发 |
| 后端更怕尖峰时 | **更合适** | 要把 `B` 设小 |
| 业务可短时扛毛刺时 | 可能过于「死板」 | **更常用** |
| 快速失败 | 桶满拒绝 | 无令牌拒绝 |

实践建议：

1. **接入层建连：** 优先令牌桶（`r` + `B`），`B` 按「可接受的瞬时握手数」设；后端极脆再用漏桶把 CPS 钉死。  
2. **限流后必须快速失败**（503/断连），并配合客户端退避（§1.2），否则重试会二次砸穿。  
3. 可对 **全局 / 每 IP / 每活动 ID** 分桶，避免一个恶意 IP 耗光全局令牌。

## 3. 协议与架构：减少「短连接」本身

### 3.1 方案 A：继续 HTTP/1.1 短连接（但必须可控）

**干什么：** 仍用常见 HTTP API，但强制 Keep-Alive、超时、限制每请求新建。  
**适用：** 简单业务、改造成本低。  
**必须做到：**

- 客户端复用连接（§1.4）  
- 服务端 `IdleTimeout` 等配齐（§4）  
- 活动高峰靠 §1、§2 消峰打散  

**做不到复用时：** 百万用户 × 每用户多次 dial = 建连风暴几乎必然。

---

### 3.2 方案 B：HTTP/2 或 gRPC（多路复用）

**干什么：** 一条 TCP 上并行多个请求（stream），少建连。  
**适用：** 中高 QPS API、服务间调用、移动端可升级协议时。  
**不是什么：** 不是自动无限容量；单连接仍有头阻塞/取消等细节，但 **建连次数** 通常降一个数量级以上。

```text
HTTP/1.1 差：  业务×N ≈ dial×N
HTTP/2：      业务×N ≈ dial×1（同主机）
```

---

### 3.3 方案 C：长连接网关 + 短任务异步

**干什么：**  

1. 边缘（长连接网关）维持用户长连接（WS/TCP）。  
2. 业务高峰时，网关只收消息，**写入 Kafka/队列**，由消费者慢慢处理。  

**适用：** IM、推送、秒杀通知、行情。  
**不是什么：** 不是「长连接网关替代所有 HTTP」；是把 **「连着」和「干重活」拆开**。

```text
用户 ──长连接──► 网关 ──入队──► Kafka ──► 订单/抽奖 Worker
                     │
                     └── 立刻回「已接受/排队中」
```

**效果：** 开闸瞬间不再等于「百万 TCP 短连接 + 百万下单事务」同时发生。

---

### 3.4 方案 D：CDN / 边缘缓存

**干什么：** 静态资源、配置、活动页 HTML、只读接口尽量在 CDN/边缘命中。  
**不是什么：** 不能缓存「下单、扣库存」；是把 **可缓存流量挡在源站外**，减少打到 Go 的连接与请求。

---

## 4. 单机 Go：高并发怎么扛（概要）

LB 分摊后，单机定容量（须压测）。原则三句：

1. **Accept 尽量不停**，超额明确失败（Close / 503），别把人堆在 backlog 假连上。  
2. **连接有上限、业务有舱壁、下游有连接池**——禁止「一连接一 G 无界打 DB」。  
3. **拒绝快于慢处理**；超时把慢客户端抠出上限。

### 怎么应对（一张表）

| 层次 | 做法 | 要点 |
|------|------|------|
| **连接软限** | Accept 后超限立刻 `Close`（能解析协议则先 503+`Retry-After`） | **主限流**；客户端马上感知 |
| **连接硬限** | `netutil.LimitListener`，Hard≈Soft×1.2，且 ≤ ulimit 余量 | **安全阀**；防 FD/内存打穿；只硬限会放大 overflow/重试 |
| **请求 in-flight** | 中间件计数，满则 503 | 保业务；不能替代连接硬限 |
| **超时** | `ReadHeaderTimeout`（必开）+ Read/Write/Idle + 下游 context | 没有超时，上限必被慢连接占满 |
| **业务舱壁** | 默认信号量满则 503；重活才用短队列+固定 worker | 按 DB/Redis/RPC **分舱**；队长了不如拒 |
| **出站池** | DB/Redis/HTTP 连接池 + `MaxConnsPerHost` | 防入站短连内部再 Dial，CPS 二次放大 |
| **减负** | `sync.Pool`、限 header/body、`GOMAXPROCS≈核数` | 降 GC/分配；不是扩容手段 |
| **运维** | `Shutdown`+LB 摘流；扩容用多实例，少玩本机 `SO_REUSEPORT` | 不扛洪峰，只止血/发版 |

```go
// 软限主路径（硬限：ln = netutil.LimitListener(ln, hardN)）
sem := make(chan struct{}, softN)
c, _ := ln.Accept()
select {
case sem <- struct{}{}:
    go func() { defer func() { <-sem; c.Close() }(); handle(c) }()
default:
    _ = c.Close()
}
```

## 5. 内核与机器参数（每个参数干什么）

这些是 **操作系统给连接排队、持有 fd 的容量**；调参是挖潜，不能替代 §1～§4。与 §0.2 四环直接对应。

| 参数 | 干什么（说人话） | 不管什么 |
|------|------------------|----------|
| `ulimit -n` / `fs.file-max` / `fs.nr_open` | 进程/系统最多能开多少文件（连接≈占 fd） | 不提高业务逻辑 QPS |
| `net.core.somaxconn` | accept 队列深度；全连接队列约 `min(backlog, somaxconn)` | 不是 Go 业务队列；**调大只推迟打满** |
| `tcp_max_syn_backlog` | 还在三次握手中的 SYN 队列 | 打满会丢 SYN，客户端重传 |
| `tcp_tw_reuse` | 仅当本机作为 **客户端主动外连** 时，有条件复用 TW 中的端口 | **不解监听侧 TW**；不替代 Keep-Alive |
| `tcp_max_tw_buckets` | TW 桶上限，防海量 TW 拖垮 | 辅助；治本仍是少短连 |
| `ip_local_port_range` | 主动出站临时源端口范围 | 纯入站监听服务次要 |
| 网卡多队列 / RPS | 建连包别都打到同一个 CPU 软中断 | — |

### 5.1 TIME_WAIT：客户端侧 vs 服务端侧

| | **主动外连侧（常见客户端/服务调下游）** | **服务端主动关闭大量入站连接** |
|--|------------------------------------------|--------------------------------|
| 卡住 | 临时 **源端口**（四元组） | **FD + 内核内存**（监听端口本身不耗尽） |
| 现象 | `Cannot assign requested address` | `Too many open files`，`accept` 失败 |
| 估算 | TW 占用 ≈ 每秒主动关闭数 × ~60s | 每个 TW socket 仍占 1 个 FD + 内核结构内存 |
| 注意 | 重启进程 **清不掉** 内核 TW | idle timeout 过短会自己制造服务端 TW 洪峰 |

**供需：** 新建消耗 > TW 回收。  
**治本：** Keep-Alive / 连接池 / H2，少产生 TW。  
**辅助：** 出站侧才考虑 `tcp_tw_reuse`；勿指望调参硬抗建连风暴。

### 5.2 系统瓶颈层级（FD → 内存 → 内核栈）

1. **FD（第一道墙）：** 默认常 1024；调高后 `Too many open files` 消失，瓶颈后移。  
2. **内存：** 空闲连接约 3～4KB 级内核开销；活跃连接含 buffer 可达数十 KB+。FD 够内存不够 → `ENOBUFS`/`ENOMEM`。  
3. **内核网络栈：** 中断、协议路径、锁竞争——冲向千万级才常谈旁路；百万短连洪峰优先把队列、TW、限流、worker 池做对。

## 6. 容量估算与压测（每个数字什么意思）

### 6.1 单机上限怎么想

```text
目标并发连接 ≈ min(
  fd 还能剩多少,
  内存 / 每连接开销（goroutine+缓冲+TLS 状态）,
  CPU 能完成的「握手+业务」速率 × 连接平均存活时间
)
```

| 形态 | 舒适区（量级，须压测） | 含义 |
|------|------------------------|------|
| 明文 HTTP，几乎无业务 | 数万连接可讨论 | 主要耗在 fd/内核 |
| TLS 短连 + 业务 | 常数千～一两万就要拆 | 握手+业务 CPU 先爆 |
| 长连接空闲为主 | 优化后单机可达更高量级 | 另一类设计，不是本文短连风暴 |

**几百万同时：** `实例数 ≥ ceil(峰值连接 / 单机上限) × 冗余系数`。  
还要压 **CPS（每秒新建连接）**，只压 QPS 不够。

### 6.2 压测该看什么（对应 §0.4）

| 指标 | 说明什么 |
|------|----------|
| CPS | 建连有多猛 |
| `listen overflow`、`ss -lnt` Recv-Q/Send-Q | accept 队列是否溢出/堆积 |
| accept 失败 / 拒绝连接数 / 503 比例 | 有没有按设计快速失败 |
| `ss -s`、临时端口、`Cannot assign requested address` | TW / 端口是否耗尽（出站侧） |
| `Too many open files` | FD 是否打满（含服务端 TW） |
| `nonvoluntary_ctxt_switches`、goroutine、GC | 调度抖动 / 协程风暴 / 内存 |
| P99、重试放大 | 往往比 QPS 更早恶化 |
| DB/Redis 延迟 | 下游是否成为炸弹 |

**口诀：** 短连接洪峰下，系统常常不是 QPS 先掉，而是 **延迟和重试先坏**。

## 7. 保护下游（连接进来 ≠ 核心业务全开）

### 7.1 准入与业务分离

**干什么：** 先过「排队/拿票」轻接口，有 ticket 才能打「下单」重接口。  
**不是什么：** 不是多此一举；是避免百万连接同时撞事务。

```text
/enter 或 /queue  → 轻：发号码牌
/order?ticket=…  → 重：校验票后再扣库存
```

---

### 7.2 有界队列 + 过载返回

**干什么：** 进程内业务队列长度固定；满了立刻 429/503，保住队列里已有的请求跑完。  
**不是什么：** 不是无限 buffer「先攒着」——无界队列会把内存撑爆（和本仓库泄漏课同一类问题：引用/堆积）。

---

### 7.3 异步化（消息队列）

**干什么：** 接入层鉴权通过后只负责 **写入 Kafka/RocketMQ/NATS**，马上返回「受理成功/排队中」；消费者按能力消费。  
**不是什么：** 不是丢消息不管；要有持久化、重试、最终一致与查询接口。  
**效果：** 峰值被队列削平。

---

### 7.4 缓存与预扣

**干什么：** 热点配置进本地/Redis；库存预扣在 Redis，异步落库。  
**不是什么：** 不是取消数据库；是让 **开闸瞬间不打爆主库**。

---

### 7.5 熔断、降级、排队页

| 手段 | 干什么 |
|------|--------|
| 熔断 | 下游挂了，快速失败，避免拖死接入 |
| 降级 | 关非核心功能（推荐、繁琐校验），保下单主路径 |
| 排队页 | 产品层挡住多余点击与连接 |

---

## 8. 推荐组合拳（按投入从低到高）

对应 §0.3 五层；每一步都是上文落地：

1. **jitter + 指数退避 + 分片开闸**（§1）— 消峰，避免同一瞬间砸穿  
2. **多 AZ 多实例 L4/L7 + TLS 卸载**（§2）— 入口收敛、打散  
3. **网关建连限流 + Go 软丢载/硬上限/HTTP 503 + 业务舱壁**（§2.5、§4）— 背压  
4. **Keep-Alive / HTTP2/gRPC + 对象池/出站连接池**（§1.4、§3、§4）— 短而不重  
5. **长连接网关或 MQ 异步**（§3.3、§7.3）— 峰值与连接解耦  
6. **内核：somaxconn / TW 分侧治理 / 端口；压测盯 overflow 与非自愿切换**（§5、§6）  
7. **熔断降级排队页**（§7.5）— 活动兜底  

**不推荐：** 单机一个 Go 二进制硬抗「几百万同时 TCP 短连接 + TLS + 业务」。

---

## 9. 一句话结论

**关键不是扛住几百万连接同时存在，而是让几百万次建连和断连不在同一瞬间压垮同一个队列。**

- **做法：** L4 卸建连压力、L7 收敛 TLS/路由/限流；Go 用软丢载+硬上限+舱壁快速背压；内核治理 accept/TW/端口（分清主被动侧）；业务用连接池、对象池、Keep-Alive 控制单次短连开销；多入口就近把洪峰切碎。  
- **验证：** 盯 overflow、TW/端口/FD、非自愿切换、P99 与快速失败比——**别只看 QPS**。  
- **单进程：** 短连看 CPS+并发上限；长连接挂机约 1 万～5 万/进程须压测；视频路数不按业务 Go 估。
