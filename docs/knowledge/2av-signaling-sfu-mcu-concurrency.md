# 音视频怎么传：信令 + 媒体（SFU/MCU）与高并发

> 和「百万 HTTP 短连接」不是一路：音视频要同时解决 **谁跟谁说话（信令）** 和 **音视频包怎么走（媒体）**。  
> 本文解释传输模型，并给出高并发架构要点。

---

## 1. 音视频传输拆成两层

用户感觉是「开着腾讯会议在聊」，服务端至少两路流量：

| 层 | 传什么 | 典型协议 | 特点 |
|----|--------|----------|------|
| **信令（Signaling）** | 进房、鉴权、房间成员、开关麦、协商编解码、ICE 候选地址 | WebSocket / gRPC / HTTP；SDP 在信令里交换 | 消息小、频率低，偏「控制面」 |
| **媒体（Media）** | 真正的声音、画面数据包 | 多为 **UDP** 上的 RTP/RTCP（WebRTC）；也可 RTMP/SRT 等 | 带宽大、延迟敏感，偏「数据面」 |

```text
手机 A                         手机 B
  │                              │
  │ ① 信令：我要进房、这是我的 SDP │
  ├──────── WebSocket/HTTP ──────┤──► 信令服务（可用 Go）
  │                              │
  │ ② 媒体：音视频 RTP 包         │
  ├──────── UDP/WebRTC ──────────┤──► 媒体节点（SFU/MCU）
  │                              │
```

**为什么要拆开：**  
- 信令可以走你们熟悉的微服务（鉴权、房间、计费）。  
- 媒体必须按 **带宽 / CPU / 就近转发** 单独扩容，不能和「订单 HTTP」混在一个 Go 进程里硬扛。

---

## 2. 信令在干什么（说人话）

信令 **不负责传画面**，只负责「把通话组织起来」：

1. 登录 / 进房鉴权  
2. 交换 **SDP**（我支持什么编码、收发端口意图）  
3. 交换 **ICE** 候选（公网/内网地址，打洞用）  
4. 房间事件：有人进/出、禁言、共享屏幕开关  
5. 可选：踢人、录制开关、布局偏好  

常见技术：

- **WebRTC 信令**：自定义 JSON over WebSocket（很多产品）  
- 信令集群：多实例 + Redis 房间状态 + 粘性或广播  

信令挂了 → 进不了房、协商失败；但 **已建立的媒体短时间有时可继续**（取决于实现）。

## 3. 媒体怎么到对方：三种拓扑

### 3.1 点对点（Mesh / P2P）

```text
A ◄──RTP──► B
```

- 适合 1v1、人少。  
- 多人时：每人要向其他每个人推流 → 上行带宽和连接数爆炸。  
- **高并发多人会议基本不用纯 Mesh。**

### 3.2 SFU（Selective Forwarding Unit，选择转发）

```text
        上行（每人推 1 路）
   A ──┐
   B ──┼──► SFU ──┬──► A（收其他人）
   C ──┘          ├──► B
                  └──► C
```

**干什么：**  
服务器 **几乎不解码、不混流**，把收到的 RTP **按订阅关系转发给需要的人**（可做选路、降分辨率订阅）。

**优点：** CPU 相对省；现代会议（腾讯会议/Zoom 类云会议）主流是 SFU 思路。  
**代价：** 下行带宽随「订阅路数」放大——人越多、每人看的流越多，出口带宽越痛。

### 3.3 MCU（Multipoint Control Unit，多方控制/混流）

```text
   A ──┐
   B ──┼──► MCU（解码 → 混成一路 → 再编码）──► 每人只收 1 路合成画面
   C ──┘
```

**干什么：**  
服务器把多路音视频 **解码、混合、再编码**，客户端只收一路「会议室合成画」。

**优点：** 客户端简单、下行省。  
**代价：** **服务器 CPU 极重**；路数一多单机很快顶满。更适合老视频会议硬件、或强依赖「一路合成」的场景。

### 3.4 SFU vs MCU 对照

| | **SFU** | **MCU** |
|--|---------|---------|
| 服务器 | 主要转发 | 解码+混流+编码 |
| CPU | 中等（加密/打包也吃） | 很高 |
| 带宽 | 下行易被订阅放大 | 下行相对固定 |
| 灵活度 | 可自选看哪几路 | 布局由服务器定 |
| 高并发多人 | **主流** | 靠堆机器，单机容量小 |

业界常见：**SFU 为主**，局部能力（录制、转直播、老终端）再挂转码/MCU 式混流服务。

## 4. WebRTC 里一次通话的简要时序

```text
1. 客户端 ↔ 信令：进房、发 offer/answer（SDP）
2. 客户端 ↔ 信令：交换 ICE candidates
3. 打洞/选路成功 → 与媒体服务器（或对端）建立 DTLS/SRTP
4. 开始发 RTP 音视频；RTCP 做丢包、码率反馈
5. 挂断：信令通知离开；媒体停止推拉
```

传输路径上常见组件：

- **STUN**：发现自己的公网地址  
- **TURN**：打洞失败时中继（也吃带宽，要单独容量规划）  
- **SFU**：房间内转发

## 5. 音视频高并发：和 HTTP 短连接的差别

| 维度 | HTTP 活动高并发 | 音视频高并发 |
|------|-----------------|--------------|
| 连接形态 | 短连 / 短 Keep-Alive 风暴 | **长连接 + 持续 UDP/RTP** |
| 瓶颈 | CPS、fd、TLS 握手、下游 QPS | **带宽、SFU CPU、UDP 丢包、跨区延迟** |
| 扩容单位 | API 实例数 | **媒体节点数 × 单机路数** + 就近接入 |
| 容量公式直觉 | QPS × 延迟 | `码率 × 订阅关系 × 人数` |

粗账（示意）：

```text
一人上行 1 Mbps
房间 20 人，每人看其余 19 人（理想最坏）
→ 下行可到约 19 Mbps/人量级（实际会用订阅降级、Simulcast 减轻）
```

所以：**「同时在线信令 10 万」≠「同时开视频 10 万路」。**

## 6. 音视频高并发推荐架构

```text
客户端
  │
  ├─信令─► DNS/LB ─► 信令集群（Go 微服务）─► Redis（房间状态）
  │
  └─媒体─► 就近接入 / Anycast
              └─► SFU 集群（按房间调度）
                    ├─► 录制 / 转码 / 旁路直播（可选）
                    └─► TURN 集群（中继）
```

### 6.1 信令面高并发要点

- 信令可水平扩；房间状态进 Redis / 专用存储  
- 大房间用 **分片广播**（不要每个事件打爆单实例）  
- 鉴权、频控防刷房  

### 6.2 媒体面高并发要点（核心）

| 手段 | 作用 |
|------|------|
| **按房间调度到 SFU** | 同房尽量同节点或同机房，减少二次转发 |
| **就近接入（华东等多区域）** | 降 RTT、降丢包 |
| **Simulcast / SVC** | 同一人推多档码率，订阅端按网速选小流 |
| **订阅降级** | 人多时默认只看说话人/缩略图，限制同时订阅路数 |
| **独立 TURN 扩容** | 中继流量别和 SFU 混无算 |
| **弹性扩 SFU** | 按「房间数 / 路数 / 出口带宽」扩，不是按 HTTP QPS |
| **录制异步** | 录制/转码拆成旁路服务，避免拖垮实时转发 |

### 6.3 单机容量怎么想（数量级，须压测）

| 角色 | 粗量级直觉 |
|------|------------|
| 信令 Go 实例 | 可接近「长连接在线」量级（万级连接需压测） |
| SFU 节点（转发、不大规模转码） | 常按 **百～低千「端」** 或 **单房间数十～一两百人** 规划 |
| MCU / 重转码 | 往往几十路就很重 |

精确数字取决于：分辨率、码率、是否加密、是否转码、网卡、是否同机房。

## 8. 一句话记住

- **信令**：谁进房、怎么协商 —— 小消息、可用 Go 微服务。  
- **媒体**：音视频包怎么走 —— 多用 **SFU 转发**；**MCU 混流吃 CPU**。  
- **高并发**：扩 **SFU + 带宽 + 就近 + 订阅降级**；别指望一个业务 Go 扛「百万路视频」。
